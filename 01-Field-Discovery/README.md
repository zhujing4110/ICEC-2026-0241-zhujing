### 人工耗时这一列：只有估算，没有实测（为什么）

审计表 `raw_data/task10-batch-audit.csv` 里只有一列人工耗时，列名直接写「估算」，没有并列的「实测」列。这是方法选择，不是缺漏：

| 列名 | 内容 | 性质 |
|---|---|---|
| `人工总耗时(分钟,估算)` | 按动作拆解推算（如重命名 8 秒/件 = 选中→F2→输入→回车→核对 5 个动作） | 估算 |
| `脚本耗时(秒,实测)` | `perf_counter()` 重复 3 次取中位 | 实测 |

**当前交付口径**：报告与表格里所有倍数都标「按估算」，只当数量级，不作结论。表里也不留空的「实测」列——空列容易被读成「忘填」，写明「估算」是明确的方法选择。

**为什么不另设实测列**：逐项掐表要再占约 1 小时人力，而它只改变「倍数」这一列的绝对值——「脚本单件成本恒定、人工随规模线性增长」这两个结论不受影响（趋势与估算的绝对值无关）。截止前这段时间给了课题 02 的采样设计与脚本，没有用来给倍数做校准。

**代价写在明面上**：倍数全部标「按估算」；局限第一条写明「人工侧为估算模型」；并预判了误差方向——熟练者实测通常**低于**估算（估算按完整 5 个动作算，实操会滑过去），所以真实倍数多半更小。宁可先说，不等面试问。

## 四、课题 04 已完成的部分

**交互版**：`task04-queue-throughput-model.html` —— 浏览器直接打开，参数可拖，图表、结论、方案表实时联动，自带 A4 打印样式。

**复算脚本**：

```bash
python tools/task04_queue_model.py      # 一条命令重算全部 6 份 CSV
```

输出到 `raw_data/`：参数表 `task04-model-params.csv`、验证表 `task04-analytic-vs-sim.csv`、食堂五方案 `task04-canteen-scenarios.csv`、电梯五方案 `task04-elevator-scenarios.csv`、λ 灵敏度 `task04-sensitivity-lambda.csv`、窗口灵敏度 `task04-sensitivity-windows.csv`。

**做了什么**：
- **食堂**：M/M/c 稳态解（Erlang-C 闭式解），`a^c/c!` 用对数域 `n·ln a − lnΓ(n+1)` 计算避免溢出，ρ ≥ 1 直接判不稳定
- **电梯**：批量服务模型，`RTT = 2(H−1)·tf + (S+1)·ts + 2K·tp`，运力 `C = m·K·60/RTT`
- **仿真验证**：食堂 60,000 人单次长运行（预热 20,000 人丢瞬态）+ 批均值 95% CI；电梯 20 组固定种子 × 30 分钟，人级事件驱动
- **方案对比**：食堂 5 方案、电梯 5 方案，每方案给 ρ、等待、积压、成本与可行性

**三个核心结论**（数字见 `report.md` 课题 04 第 3 节）：
1. ρ = 0.926 时 λ 只涨 5%，Wq 从 13.6 s 涨到 44.6 s（×3.3）；反方向加 1 个窗口，Wq 降 68%
2. 电梯基准 ρ = 1.077 > 1，是不稳定系统：每 5 分钟净积压 10.7 人，30 分钟末队列 81 人，不会自行消散
3. 目的层群控（零硬件）把 RTT 从 112 s 压到 98 s，运力 +14.3%，ρ 从 1.077 压到 0.942（转稳）

**必须说清的**：参数是教学示例值，不是现场计数。替换 `task04-model-params.csv` 里的 λ、μ、RTT 后重跑脚本即可完成标定，模型与代码不用改——这是本章唯一的缺口，也是设计上刻意留的接口。

**调试中修掉的两个单位 bug**（真实踩过，记在 `worklog/2026-11-24.md` 第十八节）：RTT 已是秒却又乘 60 → 首班车 28 分钟后才到；到达间隔按分钟累加，却与秒级发车时刻比较 → 平均候梯虚高到 880 s。

## 五、课题 02：为什么撤回，以及保留了什么

**撤回原因**：这套设计要 2 小时 06 分～2 小时 40 分的**连续挂钟时间**（四段 × 30 分钟 + 段间静置），且中途必须每 5 分钟记一次读数。截止前凑不出这样一段不被打断的时间，硬上就会断档、数据残缺。所以撤的是**申报**，不是设计。

**保留了什么**：

| 保留项 | 内容 |
|---|---|
| 采样设计 | 4 工况（待机 / 短视频 / 导航+拍照 / 高帧率游戏）× 6 时间点，按功耗由低到高排序以压缩余温累积 |
| 记录脚本 | `tools/task02_timer.py`，每 5 分钟提醒并直接写入 CSV，支持 `--mode` 断点续测 |
| 核算脚本 | `tools/task02_analyze.py`，输出段内 ΔT、最小二乘升温速率、掉电速率与收敛判定 |
| 空表 | `raw_data/task02-phone-thermal.csv`（24 行）、`task02-phase-start.csv`（仅表头），**数值全空** |

以下三段是当初写好的执行方案，**本次未执行**，留作将来补测时直接照做：

**两份数据表**：

| 文件 | 内容 |
|---|---|
| `raw_data/task02-phone-thermal.csv` | 24 行时序（4 工况 × 第 5/10/15/20/25/30 分钟），**主数据** |
| `raw_data/task02-phase-start.csv` | 每段的起点电量/温度（脚本自动写），用来算段内 ΔT |

**一次跑完四段**（跑起来就不用管，每 5 分钟响一声）：

```bash
python tools/task02_timer.py --all
```

大纲原文只要求「4 种工况各 30 分钟内每 5 分钟记录」，**没规定工况之间要冷却**——10 分钟静置是额外加的严谨性。所以有两种跑法，按剩余时间选：

| 跑法 | 命令 | 时长 | 数据质量 |
|---|---|---|---|
| 严谨（默认） | `--all` | 4×30 + 4×10 = **2 h 40** | 四段起点温度一致，可横向比较绝对温度 |
| **紧凑（时间紧时用这个）** | `--all --cooldown 2` | 4×30 + 3×2 = **2 h 06** | 段间余温叠加，只能比**段内 ΔT 与升温速率**，不能比绝对温度 |

**紧凑版必须在报告里写明**——否则等于悄悄换了口径。`report.md` 的局限段已预留这一条。

**每组只需报两个数**：电量（%）、电池温度（℃）；每段开头多报一次起点读数（也是两个数）。中途 Ctrl+C 不丢数据，续测用 `--mode 短视频` 这类单段命令。

**读数与纪律**：

- 电量看系统设置 → 电池；温度读**电池温度**（AccuBattery / DevCheck），不是电池健康度
- 全程不充电、亮度固定、连同一个 Wi-Fi；手机放桌上通风处，**别压枕头或被子上测**（散热条件会变）
- **同框照**：手机屏幕读数 + 桌面/环境 + 你的手，至少覆盖 2 种工况 + 1 张温度读数特写
- 中途室温明显变化（开空调/关窗），写进该行备注

**测完一键核算**：

```bash
python tools/task02_analyze.py
```

它输出可粘贴的时序表与分段指标（起点温度、段内 ΔT、最小二乘升温速率、掉电速率、末两点温差），并自动指出：升温最陡的工况、哪几段已接近热平衡、掉电最快的是哪段。**归因结论仍要你自己写。**
