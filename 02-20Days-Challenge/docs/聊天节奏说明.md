# 聊天节奏 · 她什么时候才开口

> 这一版解决的是"你发一句她回一句"的问题。核心三件事：
> **等你说完**、**先想一想**、**偶尔可以不接**。

---

## 一、改了什么

改之前：数据库里一出现新消息，下一轮（最多 2 秒）就生成回复发出去。
你在微信里把一句话拆成三条打，她对着第一条就抢答了 —— 后面两条她根本没看见。

改之后：收到的消息先进一个**缓冲区**，不急着回。等这条会话**安静够久**，
才把攒下来的几条合成一段，一次性回应。

```
你说：我想问个事      ← 记下，不回
你说：就是那个        ← 追加缓冲，重新计时
你说：配色怎么弄      ← 追加缓冲，重新计时
   ……安静 4~6 秒……
她回：嗯，你说的是哪块的配色
```

一次性回三条，而不是回三次。

---

## 二、三个机制

### 1. 等你说完（settle）

从**最后一条**消息开始计时，安静够 `settle_seconds` 才认定你说完了。

| 情况 | 等待时间 |
|---|---|
| 只发一条 | 2~4 秒随机 |
| 连发两条 | 3~5 秒 |
| 连发三条 | 5~6 秒 |
| 一直发个不停 | 最多 15 秒（`max_settle_seconds`）兜底，不会永远憋着 |

说得越多，越可能没说完，所以每多一条额外加 `settle_per_extra` 秒（1 秒）。

> 最初设的是 5~10 秒。实测一句「难吗」，从发出去到她开口要 **18 秒** —— 你自己回微信不会这么慢，所以压到了现在这个量级。
> 为什么不是固定值：固定 2 秒会很规律，聊几句就能感觉出来。随机在这条轴上是"像人"的关键。

### 2. 先想一想（think）

决定要回了，也不会立刻吐字。从"看到"到"发出第一条"之间有一段停顿：

```
思考时间 = 随机(0.6~1.8 秒) + 0.015 × 字数，封顶 2.5 秒
```

生成本身要调模型（通常 2~3 秒），**这段时间算在思考时间里**，不会叠加。
所以正常情况下思考这一项几乎不额外加时间，只在模型回得特别快时补一点，
让节奏不至于"秒回"。整体从发完到收到回复大约 **4~7 秒**。

### 3. 可以不接（silence）

她说"有自己的判断"，其中一条就是**有些话本来就不用接**。

判定很保守，必须同时满足：

- 这条是**纯应答**：整句只由「嗯 哦 好 行 对 是 收到 了解 哈哈 谢谢 啦 吧」这类字加标点组成
- 长度 ≤ 8 个字
- **不含**问号或疑问词（吗、怎、为、几、多少、哪、啥、谁）—— 「在吗」「然后呢」一定会回
- 这一次只发了一条（连发几条的一定回）
- 概率命中（默认 25%）
- 没有连着不回（最多空 1 次，`silence_max_streak`）

所以实际效果是：

| 你说 | 她 |
|---|---|
| 嗯 | 四次里大约有一次不回，其余回「嗯嗯」 |
| 哈哈 | 同上 |
| 收到 | 同上；但如果上一条她已经没回了，这条**一定**回 |
| 在吗 | 一定回 |
| 还行 | 一定回（"还"不在白名单里） |
| 嗯，那明天几点 | 一定回（有疑问词） |

**不接的时候，这条消息不会被记进对话历史**，所以下一轮她不会莫名其妙地接上一句"嗯"。

## 三、参数在哪改

`config.json` → `pacing` 段：

```json
"pacing": {
  "enabled": true,
  "settle_seconds": [2, 4],
  "settle_per_extra": 1.0,
  "max_settle_seconds": 15,
  "think_seconds": [0.6, 1.8],
  "think_per_char": 0.015,
  "think_max": 2.5,
  "allow_silence": true,
  "silence_probability": 0.25,
  "silence_max_streak": 1
}
```

**`pacing` 和 `burst` 两段支持热更新**：保存 `config.json` 后最多 2 秒自动生效，
不用重启，日志里会出现一行

```
节奏参数已热更新（pacing）：等 [2, 4] 秒 / 想 [0.6, 1.8] 秒 —— 不用重启
```

改坏了 JSON 也不会崩，会保留上一次的参数并打一条警告。
其他段（账号、api_key、behavior 等）仍然只在启动时读，那些改完要重启。

### 常见调法

| 想要的效果 | 怎么改 |
|---|---|
| 还要更快 | `settle_seconds` 改 `[1, 2.5]`，`think_seconds` 改 `[0.3, 1]` |
| 再稳一点、别抢话 | `settle_seconds` 改 `[4, 7]`，`settle_per_extra` 改 `1.5` |
| 一次都不许不回 | `allow_silence: false` |
| "不回"再少见一点 | `silence_probability` 调到 0.1 |
| 完全关掉这套 | `enabled: false`（回到收到就回） |

## 四、和「连发」的关系

之前做的连发（一条回复拆成两条发）和现在的等待是两件事：

- **等待**：管她要等多久才开口
- **连发**：管她开口后是一句还是两句

两个一起开着，最像真人的状态是：你发三条 → 安静几秒 → 她回两条短的。

还有一个细节：他连着发几条时，提示里会额外告诉她
"他刚连着发了几条，是一个意思，不是三个问题，挑真正值得接的那一点回"。
否则模型容易一条一条答，比抢答还像客服。

真实对比（同一句三条）：

```
原话：明天要去学校 / 还得带作品集 / 不知道带哪几份
没提示：带几份啊 | 挑自己最满意的呗，学校要展示还是交作业？
有提示：带作品集去学校，是给老师看还是交作业？
```

没提示的那版只接住了第二句；有提示的接住了整件事。

## 五、验证过什么

`pacing-test.py` 是离线测试（不连微信、不调模型），覆盖：

1. 纯应答判定：「嗯/好的/收到/哈哈/在吗/还行/嗯，那明天几点」全部分类正确
2. 等待时长：单条落在 2~4 秒，三条 4~6 秒，都不超过 15 秒上限
3. 思考时长：短句 0.9~1.6 秒，长句封顶 2.5 秒
4. **连发三条 → 只回一次**，合并文本完整，`multi` 标记正确
5. 刚发完立刻扫描 → 不回（证明真的在等）
6. 把静默概率钉死成 1.0 后：第一次「嗯」不接、第二次必接，「静默一次 + 回复一次」的实际发送数正好是 1
7. `enabled: false` 时回到即时回复

`reload-test.py` 验证热更新：改 `config.json` 后参数立刻换成新值、重复调用无副作用、
把 JSON 写坏时保留上一次的参数且进程不崩。

跑法：

```bash
python pacing-test.py
python reload-test.py
```

## 六、已知边界

- **缓冲区在内存里**。如果你正好在她等的这几秒里重启机器人，那条消息不会补回（水位已经推进了）。窗口只有 2~4 秒，实际撞上概率很低。
- **一次只处理一个会话**。她在生成回复时会阻塞主循环几秒，这期间别的会话的消息要等下一轮才进缓冲，不影响正确性，只是稍慢。
- **静默不写历史**。这是有意的，避免她下一轮接一句不存在的"嗯"。代价是模型不知道你说过这句 —— 对纯应答来说无所谓。
