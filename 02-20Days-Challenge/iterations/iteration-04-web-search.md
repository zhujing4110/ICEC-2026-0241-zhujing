# 迭代 04 · 按需联网检索

- 日期：2026-11-21
- 类型：能力扩展
- 影响文件：新增 `src/websearch.py`；`src/bridge.py`（`maybe_web_answer`）；`src/config.json`

## 需求

用户问："我和她讨论的时候她能不能在网络上获取信息。"

约束是不能让每条消息都变慢——闲聊占绝大多数，如果每条都联网，每条都要多等 3 秒。

## 选型：先测通不通，再谈方案

没有直接假设"用百度"，而是先测四个入口在你这条线路上的真实表现：

| 入口 | 结果 | 判定 |
|---|---|---|
| DuckDuckGo | 10 s 超时 | ❌ 不可用 |
| 百度 | 返回 2649 字节，页面含"验证" | ❌ 反爬拦截 |
| 搜狗 | 200，1.5 s | △ 可用但不稳 |
| **cn.bing.com** | 200，0.4 s，104 KB，10 条干净结果 | ✅ 采用 |

同一个词"深圳今天天气"，Bing 能稳定解析出 10 条标题 + URL，无验证码。

## 实现

### 触发：约定标记而不是 function calling

提示词里要求："遇到实时信息时，**整条回复只输出一行** `SEARCH: 关键词`"。程序侧：

```python
m = SEARCH_RE.search(raw)
if not m or len(raw.strip()) > 80:   # 长度限制防误判
    return raw
```

命中后执行检索，再以 `assistant(SEARCH行) + user(资料+指令)` 的形式二次生成。

选它不选 function calling 的理由：所有中间态（模型想查什么、查到什么、第二次用了哪份资料）都落在日志里，逐行可回溯。

### 天气：搜索引擎抓不准，改走结构化接口

"深圳今天天气"在 Bing 上的附件只有「深圳天气网为您提供 24 小时预报」这种导航文字，**没有一个温度数字**。第一次实测回答是"没查到深圳今天具体多少度"，等于没用。

改为天气单独走 `wttr.in`：

```
深圳 ☁️ 20°C 体感 18°C 湿度39%
北京 ☀️  4°C 体感  0°C 湿度32%
```

城市名从问题里用正则剥离噪声词得到（`今天|天气|怎么样|会|吗`等），"深圳今天天气"→"深圳"。

### 兜底：IP 定位不可靠

不说城市时按出口 IP 定位，实测定到了郑州（34.77, 113.72），与实际所在地不符。改为配置项 `web_search.default_city` 固定为深圳。

## 实测（端到端，含二次生成）

| 输入 | 是否联网 | 回复 | 耗时 |
|---|---|---|---|
| 深圳今天天气 | ✅ | 深圳今天多云，20 度，湿度不高，风有点大 | 4.4 s |
| 今天天气咋样 | ✅（默认城市生效） | 深圳今天多云，20 度，湿度不高 | 3.7 s |
| DeepSeek 最新模型是啥 | ✅ | 好像是最新出了个 V4.1 Flash，11 月发的 | 3.0 s |
| 你好呀 | ❌ | 嗯，你好呀 | 1.2 s |
| iPhone 17 现在多少钱 | ✅ | 具体价格没查到，只看到涨价和换购的消息 | 3.1 s |

最后一条是能力边界的诚实体现：Bing 摘要里没有价格，模型被约束为"查不到就直说"，而不是编一个数字。

## 遗留

- **延迟翻倍**：联网回复 3–4.4 s，微信端没有"正在输入"提示，用户感知为卡顿
- `read_top=1` 抓首条正文有时抓到无关内容（如天气网首页混入其他城市列表），目前靠模型自己判断取舍
- 商品实时价格、需登录的内容基本查不到，属已知边界
- 每小时上限 30 次，滑动窗口控制，防止异常刷取
