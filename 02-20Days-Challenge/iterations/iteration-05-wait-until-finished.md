# 迭代 05 · 从"一问一答"改成"等他说完再答"

- 日期：2026-11-24
- 类型：交互行为重构
- 影响文件：`src/bridge.py`（`handle_chat` 拆成"收"与"答"两段）；`src/config.json`（新增 `pacing` 段）；`src/persona.md`；`src/webui.py`
- 验证脚本：`tests/pacing-test.py`、`tests/reload-test.py`

## 现象

使用者的原话是："不用我说一句话就回我一句，要有自己的思考、可以选择不回；我一句话解释不清的时候，要等我把话说完。"

第一版按字面实现了：收到消息后等 5–10 秒（每多一条 +2 秒，上限 45 秒）再回答，并允许一定概率不接话。结果第二天被推翻：

> "现在中间间隔太长了可以缩短一些。"

日志里的证据是硬伤——**15:15:30 收到「难吗」，15:15:48 才发出去，18 秒**。中间没有任何网络或模型耗时，全部是程序自己在等。另一条「好」被静默策略吞掉，使用者的体感是"发出去没反应，像是坏了"。

## 定位

两个独立问题被混在同一个需求里：

1. **抢答**：`poll_once` 一读到新消息就立刻生成回复。使用者习惯把一句话拆成三四条发，第一句到达时后面还在打字，于是回复总是接在半截话上。
2. **参数拍脑袋**：第一版的 5–10 秒是为了"像真人思考"定的，但真人的停顿取决于**对方还在不在打字**，不是固定秒数。固定等人只会让人觉得程序卡了。

## 修复

### 1. 收与答分离

`handle_chat` 不再生成回复，只做三件事：把消息追加进 `pending[user]`、推进水位、记录 `first_at / last_at`。真正的回复搬到新的 `_answer()`，由主循环每轮的 `maybe_answer_pending()` 决定何时调用。

等待时长改成两段：

```
settle_delay = random(2,4) + 1.0 × (条数-1)，上限 15 秒   # 等他还发不发
think_delay  = random(0.6,1.8) + 0.015 × 字数，上限 2.5 秒  # 想一下
```

`settle` 计时从**最后一条**消息算起，所以对方每补一句，等待窗口就往后顺延——这正是"等他把话说完"。

### 2. 多条当一整段听

合并多条时给 system 追加一句「他在连着发，当一整段听，别一条条答」。这一句的效果比预想大：没有它时只接住最后一句（问"来得及吗"就只答来得及），有它时能接住整件事。

### 3. 允许不接，但不能连着不接

`_should_stay_silent()` 只对"纯应答词"（嗯/哦/好/哈哈/收到…）生效，概率 0.25，且 `silence_max_streak=1`——连着两条都不理就强制回一次，避免像掉线。

### 4. 参数热更新

节奏参数需要反复微调，而进程重启一次代价很高（要重新绑定窗口、重新登录）。`maybe_reload_live_cfg()` 每轮比对 `config.json` 的 mtime，只热替换 `pacing / burst / stickers` 三段，其余配置仍需重启。JSON 写坏时保留旧值并 warning，不更新 mtime，下次继续重试。

## 验证

`tests/pacing-test.py` 7 项离线全过（不连微信、不调模型，用临时 STATE_PATH 避免污染真实状态）：

- 单条等待落在 2–4 秒区间
- 三条连发时窗口顺延、只产生一次回复
- 合并后的 prompt 含"当一整段听"
- 纯应答词按概率静默、非应答词不静默
- 连续静默不超过 1 次
- 空 pending 不触发
- 等待期间到达的新消息不丢

`tests/reload-test.py` 3 项：改 config 后下一轮生效 / 重复调用无副作用 / 坏 JSON 保留旧值。

改完后的真实日志（`process_logs/runtime-2026-11-24.log`）：

| 收到 | 发出 | 间隔 | 说明 |
|---|---|---|---|
| 16:49:48 | 16:49:56 | 8 s | 含一次工具申请，纯等待约 4 s |
| 16:50:31 | 16:50:35 | 4 s | 单条短句 |
| 16:51:12 | 16:51:20 | 8 s | 两条连发 |
| 16:51:36 | 16:51:45 | 9 s | 两条连发 |

从 18 秒压到 4–9 秒，且不再出现"接半句"的情况。

## 遗留

- 热更新只覆盖三段配置，改端口、改开关仍需重启
- 等待窗口对"正在输入"没有感知，只能靠"最后一条消息的时间"近似
- 静默策略仍是固定概率，没有根据对话内容判断"这句到底要不要接"
