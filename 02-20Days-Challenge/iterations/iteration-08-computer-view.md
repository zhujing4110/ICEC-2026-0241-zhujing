# 迭代 08 · 让她"看"电脑：function calling + 截屏 OCR + 逐步审批

- 日期：2026-11-24
- 类型：能力扩展（新增工具调用链路）
- 影响文件：新增 `src/desk.py`；`src/bridge.py`（`deepseek_tool_chat` 与三段式审批）；`src/webui.py`（「她的电脑」卡片）；`src/config.json`
- 验证脚本：`tests/desk-test.py`（34 项）、`tests/desk-flow-test.py`（35 项）、`tests/desk-webui-test.py`（26 项）

## 需求（使用者自己定的三条边界）

1. 能力：**只读查看**（不动文件、不运行命令）
2. 时机：**每一步都要他批准**
3. 窗口：要能看到**她的操作步骤 + 实时屏幕画面**

这三条决定了实现形态，也决定了后面的大部分难点。

## 三个前置事实（都是实测出来的）

### 1. 模型支持原生 function calling

此前一直在用文本协议（`SEARCH:` / `STICKER:`）。这次试了标准 tools：

```json
{"finish_reason": "tool_calls",
 "tool_calls": [{"function": {"name": "look_screen", "arguments": "{}"}}]}
```

结构标准、参数是合法 JSON，比文本协议干净得多。**但有一条坑**：`tool_calls` 非空时 `content` 是空串，这是正常返回，不能当成 `finish_reason=length` 的截断去翻倍重试（第一版就是这么写错的，会重复请求两遍）。

### 2. 她看不到画面，只能看到字

模型没有视觉能力。所以"看屏幕" = 截屏 → Windows 自带 OCR → 文字进上下文。

**这一条必须在 prompt 和文档里写死**，否则她看到 OCR 出来的半截句子会开始编画面内容。

### 3. UIA 不能当主路径，OCR 需要放大

| 尝试 | 结果 |
|---|---|
| UIA 读窗口树 | Electron 应用（`Chrome_WidgetWin_1`）UIA 树是空的；资源管理器只读到窗口按钮 → ❌ 不可行 |
| 截屏 + OCR（原尺寸） | 「需求」认成「求」，「给」认成「蛤」 |
| 截屏 + **放大 2 倍** + 灰度 + 对比度 1.6 | 明显改善，整屏 0.9 秒约 1400 字 ✅ |

OCR 走 `winrt.windows.media.ocr`（本机语言 `zh-Hans-CN`），依赖要单独补 `winrt-Windows.Media.Ocr / Graphics.Imaging / Storage.Streams / Foundation / Globalization / winrt-runtime`——前四个装了还会缺 Globalization。

## 实现

### 工具集（5 个，全部只读）

| 工具 | 作用 |
|---|---|
| `look_screen` | 截屏 + OCR，返回屏幕上的文字 |
| `list_dir` | 列目录 |
| `read_file` | 读文本文件（拒绝二进制 / 超大 / 超长） |
| `find_files` | 按关键词找文件 |
| `sys_info` | 系统信息（时间、电池、前台窗口标题） |

### 两道安全阀

1. **路径沙箱** `resolve()`：只允许工作区与桌面/文档等白名单根，deny 掉 `.venv / venv / __pycache__ / site-packages`。
   实现时踩了一个顺序坑：**先查全局 deny 再查 allow 根，会把"允许根本身就在 AppData 下"（临时目录）自己否掉**。正确顺序是先命中 allow 根，再对相对部分查 deny。
2. **密钥打码** `mask_secrets()`：`sk-`、`api_key`、`token` 一律替换成 `***`。读文件时也会打码，避免她随口把密钥念给对方。

### 三段式异步审批

审批**不能同步阻塞**——否则主循环卡住，微信消息读取得慢，整个机器人像死机。

```
模型返回 tool_calls
  → 只登记，不执行，回一句「等我看一眼（去控制台点个允许）」
  → 使用者在控制台点允许
  → desk_results 排队
  → 主循环 maybe_resume_desk() 带着工具结果继续生成，她再说结论
```

`approve_desk()` 加了 `req["done"]` 标记：**双击或网络慢会提交两次，导致工具执行两遍**——这是测试抓到的真 bug，不是假想。

### 控制台

「她的电脑」卡片：待批条（黄底）+ 实时画面（10 秒刷新，页面隐藏时暂停）+ 操作流水。实时画面是现截 jpeg 900px q55，约 47 KB，不占带宽。

## 验证

### 工具调用倾向（10 个场景，真实模型）

| 场景类型 | 期望 | 结果 |
|---|---|---|
| 该调工具（"看我屏幕"、"桌面有几个文件"、"我那个作品集在哪"） | 调 | **4 / 4 全调** |
| 不该调（"在吗"、"今天几号"、"帮我想个文案"） | 不调 | **6 / 6 零误触** |
| 越界（"帮我把文件删了"、"改一下这个文档"） | 拒绝 | **2 / 2 正确说"只能看，动不了"** |

参数质量也正常：`list_dir{"path":"桌面"}`（会用中文别名）、`find_files{"keyword":"作品集"}`、"看我在干嘛" → `look_screen + sys_info` 同时调。

### 看到内容后的回复（无编造）

> "十个文件，八个是快捷方式……就两个真东西：LSTM 那个 pptx 和车牌识别汇报的 pptx"

> "在折腾 WorkBuddy 那个控制台面板吧，写能力说明那块"

这两句都是从 OCR 出的文字里读出来的，没有编画面。

### 回归

`desk-test.py` 34 项（8 种路径沙箱、越权不执行、密钥打码、二进制/超大/超长拒绝、找文件、真截屏 + OCR、流水、截图上限 24 张），`desk-flow-test.py` 35 项（申请不执行、控制台可见、允许→执行→继续说、拒绝→她知道没看到、重复批准被挡、超时、闲聊不碰、沙箱在工具层兜住、关开关），`desk-webui-test.py` 26 项（状态 / 实时画面 47 KB / 截图往返 / 4 种越权 404 / 重复批准 / 关闭后 503）。

真实链路（`process_logs/runtime-2026-11-24.log`）：

```
16:49:48 收到：你能看到我的电脑了吗
16:49:52 她申请看电脑：看一眼你现在的屏幕 —— 等你在控制台点允许
16:49:56 已回复：等我看一眼（去控制台点个允许）
16:50:02 批准执行 look_screen：截屏并读出 33 行字
16:50:07 已回复：能看到，你在小予控制台那个页面上
```

从申请到给出结论 15 秒，其中 10 秒花在等使用者点批准，工具本身约 5 秒。

## 遗留

- **每步都要批准，一次事可能要点 2–3 次**。做过"5 分钟内同类自动允许"的设计，但会偏离使用者明确选的"每步都批"，没有做
- OCR 对界面小字、浅色字识别率仍有限；滚动区域只能看到当前一屏
- 只能看，不能操作。使用者后来提过"能不能以录屏的方式传给你"——录屏抽帧需要视频解码，本轮未做
