# 迭代 09 · 日志没按日切分，把「每日同步」变成了不可能

- 日期：2026-11-24
- 类型：**未修复缺陷（已定位 + 方案已验证，未合并）**
- 影响文件：`src/bridge.py`（`setup_logging`）、`process_logs/`
- 关联评分点：阶段二 ①「连续不少于 7 天的运行日志，**每日同步至 `process_logs/`**」

## 现象

`process_logs/` 里只有两份日志切片：`runtime-2026-11-21.log`（439 行）与 `runtime-2026-11-24.log`（317 行）。
但程序从 11-21 起一直在用（11-22 建仓、11-23/11-24 两天连续改代码并跑测试）。
**程序跑了 4 天，日志只能交出 2 天。**

## 定位

`setup_logging()` 用的是：

```python
logging.basicConfig(filename="logs/bridge.log", mode="a", ...)
```

三个特征叠加，导致跨天无法切分：

1. **单文件追加**：从 11-21 15:47 第一次启动起，所有进程都写同一个 `bridge.log`；
2. **行内只有时间没有日期**：格式是 `%(asctime)s` + `HH:MM:SS`，`2026-11-24 16:49:01` 里那半截日期根本没写进去；
3. **重启也不分文件**：`bot.pid` 单实例锁只管进程唯一，不涉及文件名。

结果：**事后无法从内容上判断哪一行属于哪天**。`process_logs/` 里那两份切片，是靠「在某个时点手工复制一份」得到的，
日期由复制时刻决定——这不是「日志造假」，但也确实**不等于按日归档**。

## 影响（按严重度排）

| 影响 | 说明 |
|---|---|
| 直接丢分 | 项目四的日志分（25 分）隐含「连续 7 天且每日同步」。本项只能证明 2 天，且 11-22、11-23 无切片 |
| 无法自证在线 | 面试若问「11-23 你在跑吗」，只能答「在，但日志没留日期」——证据链断在工具层 |
| 排障成本 | 跨天对齐时间线要人工推算，11-23 日志里那次 18 秒等待的复现就吃过这个亏 |

## 修复方案（已验证，未合并）

`TimedRotatingFileHandler` + 纯日期后缀：

```python
from logging.handlers import TimedRotatingFileHandler

h = TimedRotatingFileHandler(LOG_PATH, when="midnight", backupCount=30, encoding="utf-8")
h.suffix = "%Y-%m-%d"        # 默认后缀是 %Y-%m-%d_%H-%M-%S，改成纯日期才能直接对应 process_logs 的文件名
h.setFormatter(logging.Formatter("%(asctime)s %(levelname)s %(message)s", "%Y-%m-%d %H:%M:%S"))
```

本地把 `when="S", interval=1` 压成秒级跑了一遍验证切分行为：

```
目录内容: ['bridge.log', 'bridge.log.2026-11-24']
活动文件内容: 2026-11-24 17:50:37 INFO 第二段：应触发切分
```

切分后旧段落到 `bridge.log.2026-11-24`，文件名直接就是 `process_logs/` 要的日期口径，可原样复制归档。

## 为什么当天不改

1. **代码已冻结**：11-23 就定了「代码侧不再改」，提交日动 logging 配置，风险收益不对称；
2. **改了也只对未来生效**：历史日志没有日期戳，无法追溯补切，改完对本次提交一分不加；
3. 真要补，得用 `state.json` 里带时间戳的消息记录去反推——那是**旁证**，不是日志，不应混进 `process_logs/`。

## 教训

可观测性要按**评分口径**设计，不是按「能看就行」设计。
要求「每日同步」，日志就该天然按日成文件；等要交材料时才发现切不出来，是设计时没把「归档」当成需求的一部分。
