## 脱敏规则（为什么日志里是"主号A/小号B"）

原始日志包含两个真实微信号的 wxid 和昵称。这两个号仍在日常使用，直接公开等于把账号 ID 暴露在公网。所以做了机械替换，**只改标识，不改任何时间、内容、耗时、报错**：

| 原始 | 替换为 |
|---|---|
| 真实 wxid（主号） | `wxid_MAIN_MASKED` |
| 真实 wxid（小号/机器人） | `wxid_BOT_MASKED` |
| 主号昵称 | `主号A` |
| 小号昵称 | `小号B` |
| 本机绝对路径 | `<项目目录>` |
| API Key | 从不写入日志；`config.example.json` 中为占位符 |

替换后用正则复查过，无残留的 `wxid_` 真实值、`sk-` 密钥串和本机用户名路径。

关键事件对应的时间点与迭代记录：

- 全篇 49 处「先等他说完（已攒 N 条）」——合并窗口在累计条数（见 iteration-05）
- `16:04:42` / `16:26:44` 表情包发送成功（见 iteration-06）
- `16:22:35` / `16:23:52` 收到非文本消息并被识别成 `[他发来一个表情包：怎么这样]` / `[他发来一个表情包]`（见 iteration-07）
- `16:49:52 → 16:50:02 → 16:50:07` 看电脑的完整三段式：申请、批准执行、带着结果继续说（见 iteration-08）
- `16:51:00` / `16:51:34` 两条连发（`已回复（2 条）`），同一条消息只处理一次
- `16:51:02` 「记住 1 条新事实」——回复发出后才起后台线程做记忆提取，不占回复延迟

## 局限

两份日志合计约 3 小时运行片段，不是连续 7 天。程序本身没有做日志轮转与长期归档：单文件累积到一定体积后需要手工切分，这是后续要补的（见主 README 第六节"已知缺陷"）。
