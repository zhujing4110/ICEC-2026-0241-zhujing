## 三、15:09–15:21 节奏改造：从"一问一答"到"等他说完"

使用者原话："不用我说一句话就回我一句，要有自己的思考、可以选择不回；一句话解释不清的时候，要等我把话说完。"

**做法**：`handle_chat` 拆成"收"与"答"两段，新增 `pending` 队列与 `maybe_answer_pending()`；等待 = `settle`（等他还发不发）+ `think`（想一下）。

第一版把 `settle` 定成 5–10 秒、静默概率 0.5。**半天后被数据推翻**，见下一节。

## 六、15:46–16:00 表情包触发率：161 条回复只出 1 张图

使用者改完库后反馈"出图概率很低"。先量化：**161 条文字回复，1 次带图（0.6%）**。

逐道统计五道闸，三个真原因都在"模型压根没写 `STICKER:` 行"这一层：

1. persona 与 system prompt 里**两条"少发"指令叠加**（"十次里一两次"）
2. 模型**不知道库里有哪些标签**，自己造词（`STICKER: 喜滋滋`、`STICKER: 烦`）→ 挑不到图
3. `max_tokens=150` 把最后一行 `STICKER:` **截掉**，且正文非空时不重试 → 静默丢失

对照实验：150 → 2/10，400 → 4/10。

修完之后同一批 10 个情绪场景：**10% → 40%**（4 条配图，3 条挑到图，1 条因库里没有"累了"落空）。

顺带修掉一个语义反转 bug：子串匹配让「喜滋滋」命中标签「不开心」。

## 七、16:14 非文本消息：不是"没回"，是"没看见"

`handle_chat` 里有一行 `if m.get("type") != "文本": continue`——非文本消息在这里被丢弃，**但水位照常推进**，于是永久丢失，日志里连一行都不留。

摸清三个事实后才有解：

- 表情 XML 里的 `md5` **就是原图 md5**，可以和自己库精确匹配
- `cdnurl` 直接 GET 返回**明文 GIF**（本地 `cache/Emoticon/` 下的加密文件解不开）
- 卡片消息的标题是**子元素** `<title>`，不是属性（一开始按属性解析，全空）

新增 `inbox.py`，把任何非文本消息转成一行 `[他发来一个表情包：无语]`，`pending` 增加 `parts` 保留顺序。**她背后的模型没有视觉能力**，所以 prompt 里写死：别夸图、别猜图、别承诺"我打开看看"。

## 八、16:40–16:51 只读看电脑：function calling + OCR + 逐步审批

使用者要求三条边界：**只读 / 每步都要他批准 / 要看到操作步骤和实时画面**。

三个前置事实：

1. 模型**支持原生 function calling**（`finish_reason=tool_calls`）。坑：`tool_calls` 非空时 `content` 是空串，这是正常返回，不能当截断去翻倍重试
2. 模型**没有视觉**，所以"看屏幕"= 截屏 → Windows OCR → 文字进上下文
3. UIA 读不了 Electron（树是空的），OCR 必须**放大 2 倍**再认（原尺寸「需求」→「求」）

审批做成三段式异步：模型返回 `tool_calls` → 只登记不执行 + 回一句"等我看一眼" → 使用者点允许 → 主循环带着结果继续生成。**不能同步阻塞**，否则主循环卡住、微信消息读得慢。

实测：该调工具的 4/4 全调，不该调的 6/6 零误触，越界请求 2/2 正确拒绝。看到屏幕后的回复是"十个文件，八个是快捷方式……就两个真东西"，没有编造。

### 踩到的两个坑

1. **`--append` 仍会问"按回车开测"**，把 stdin 的第一行吃掉，导致整体错位一行、最后一组没写进去。改成续记时跳过该确认。
