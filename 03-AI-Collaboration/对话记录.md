# AI 协作排障记录

原则：AI 给方案，我负责验证。方案错了要能拿日志反驳它——这份记录里保留了两次"AI 判断错、被日志推翻"的过程。

---

## 1. 需求澄清：先问边界，再动手

**我的提问**："微信官方有没有开放个人号自动回复的接口？别人的号能不能加它聊天？"

**AI 给的**：ClawBot / iLink 通道，LangBot 有现成适配器，扫码登录即可。

**我验证的**：按它说的部署跑通了（Docker + LangBot 4.11.2 + `openclaw_weixin`），日志确实出现完整回复。但形态不对——只有扫码的号自己能和它聊。

**修正**：追问"其他用户能否添加"，AI 才引到官方文档原文：「ClawBot 是你与你自己的 AI 之间的私密通道，其他用户无法添加或触达」。

**教训**：AI 会告诉你"能跑通"，但不会主动告诉你"跑通了也不是你要的形态"。**需求边界要专门问一次。**

### 一次 AI 判断错、被日志推翻的记录

AI 曾说：日志里 `person_o9cq...@im.wechat` 和机器人 `660eec...@im.bot` 不是同一个号，"说明确实是另一个微信号发来的"。

我要求它复查文档后推翻了这个结论：这两个只是"用户身份"和"机器人身份"两套 ID，发消息的一直是自己。**AI 从日志形态做推断，但不知道产品定义。**

## 2. 环境搭建：Windows 的坑比代码多

| 问题 | AI 首轮建议 | 实际结果 | 最终做法 |
|---|---|---|---|
| WSL 未启用 | 用 `dism` 脚本启用可选功能 | 报 0x800f0906，缺本地安装源 | 改用 `winget install Microsoft.WSL`（MSIX 包，不需要可选功能） |
| bat 脚本乱码 | 生成的脚本是 UTF-8 | cmd 按 GBK 解析，全变问号 | 重写为纯 ASCII，并校验非 ASCII 字节为 0 |
| 提权被拦 | `Start-Process -Verb RunAs` | 被安全策略拦截 | 放弃自动提权，改为提示手动操作 |
| 拉镜像超时 | 默认源 | 卡住 | 配镜像加速（daocloud / 1panel） |

## 3. 依赖安装：pip 源与预编译包

**现象**：`pip install` 连 `requests` 都拉不下来。

**AI 的诊断过程**：先怀疑代理 → 打印 `pip config` 和 env 里的 proxy → 发现配置正常 → 分别测清华源 / 官方源 / 阿里云源 → 确认是**清华源在你这条线路上不通**。

**结论**：换阿里云源，`[solution] 秒级下载`。

**另一个坑**：`winsdk` 没有 Python 3.13 的预编译 wheel，pip 尝试从源码编译（需要 VS Build Tools）。

**解决**：`pip install wechatauto-replica --no-deps` 跳过依赖，再单独装缺的那几个包——因为该库的核心功能（读库、发消息）不依赖 `winsdk`，它只影响可选特性。装完后 `import wechatauto` 正常。

**教训**：遇到"某个依赖装不上"，先判断它是必需依赖还是可选依赖，不要为了一个边缘包去装几个 G 的编译工具链。

## 4. 通道验证：`errcode=-14`

**现象**：扫码显示成功，发消息没反应。

**AI 的判断**：`-14 = session timeout`，多半是多个进程抢同一个微信会话。

**验证**：确实同时开着测试脚本和 LangBot 自身的登录进程，两边互顶，扫一次掉一次。

**解决**：只保留一个进程做登录，其他全部停掉，一次扫码成功。

## 5. 缺陷排查（最能体现协作价值的部分）

### 5.1 发送 13 秒

**我的提问**："回复要等十几秒，是不是模型太慢？"

**AI 的做法**：不猜，直接分段计时——测出模型只占 1 秒，剩下 13 秒全在 `send_msg`。

**进一步**：对比 `who=wxid` 与 `who=显示名` 两种传参，13 s vs 1.4 s，再让 AI 读库源码确认原因（wxid 每次重开会话搜索）。

**这一段的价值**：AI 没有接受我"模型太慢"的前提假设，而是先测量再归因。

### 5.2 双实例重复回复

**我的提问**："有时候会收到两条不一样的回复。"

**AI 的做法**：先看日志时间窗（同一消息两次处理）→ 再查进程列表，发现两个 `bridge.py` 实例（15:49 与 15:58 启动）。

**关键发现**：之前的 `TaskStop` 只杀掉了 venv 的 python.exe 包装进程，真实解释器还活着。

**修复后自己踩的坑**：单实例检测写成"cmdline 含 bridge.py 字符串"，结果把检测脚本自己也判成了实例。改为判断"前两个参数中是否有以 bridge.py 结尾的项"。

### 5.3 回复太长

**我的提问**："回复还是很长很复杂。"

**AI 的归因**：不是提示词不够狠，是 `max_tokens=800`、`max_reply_chars=300` 且只做中间截断。

**我要求它拿数据说话**：于是它把同一个裁剪函数在 32 / 40 两个阈值下的输出并排打出来，才定下 32。

### 5.4 "等我说完"：第一版参数是拍脑袋的

**我的提问**："不用我说一句就回一句，要有自己的思考，一句话解释不清的时候要等我说完。"

**AI 的做法**：把收消息和回消息拆开，加了一个 5–10 秒的等待窗口，还允许一半概率不接话。

**第二天我推翻了它**："间隔太长了。" 它去翻日志，找到 15:15:30 收到、15:15:48 才发的记录——**18 秒，全是程序在等**。参数改成 2–4 秒后，实测落到 4–9 秒。

**教训**：AI 会把"像真人"翻译成一个具体数字，但这个数字它是猜的。**任何以秒为单位的参数，都要拿真实日志对一遍。**

### 5.5 表情包："感觉发得少"不是证据

**我的提问**："我改了库，但平时出图的概率很低，她的判定是怎样的？"

**AI 的第一反应**是猜"提示词太保守"。我要求它先统计，于是它去数日志：161 条回复里只有 1 次真带图（0.6%），五道闸逐个数完，三个真原因（双重"少发"指令、模型自造标签、`max_tokens` 把最后一行截掉）都不是最初猜的那个。

**这一段最有用的是方法**：把"概率低"拆成"哪一道闸拦的、拦了几次"，而不是继续改提示词试试看。

### 5.6 看电脑：AI 先给了个错方向

**我的提问**："能不能给她一个窗口，让她能看电脑上的东西。"

**AI 的第一版方案**是用 UIA 读窗口树。实测发现 Electron 应用的 UIA 树是空的，资源管理器只读到窗口按钮——**这条路根本走不通**。

改走"截屏 + Windows 自带 OCR"后还有第二个坑：原尺寸识别把「需求」认成「求」。放大 2 倍才正常。

**教训**：涉及系统能力时，AI 给的 API 名往往是对的，但**"这条路在你的环境里能不能用"必须自己跑一遍**。

### 5.7 我踩的坑，不是 AI 的

有两次测试脚本往真实的 `state.json` 里写了假数据，把真实会话历史污染了，都是事后发现的。第三次才养成习惯：**创建对象之前先把路径指向临时目录**。

这条记在这里是因为它说明一件事：AI 写的测试也会破坏真实数据，**跑测试之前要先看它会写哪里**。

## 6. 沉淀下来的提问模式

| 场景 | 有效问法 |
|---|---|
| 选型 | "先用 X 有什么代价、什么时候会撑不住？"（而不是"X 好不好"） |
| 排障 | "这是日志，帮我定位是哪一段占了时间"（给证据，不给结论） |
| 验证 AI 的说法 | "这个结论的依据是文档还是你的推断？" |
| 参数调优 | "把 32 和 40 两档的实际输出都打出来对比" |

反面问法："帮我写个微信机器人" —— 会得到一堆跑不通的代码，因为模型不知道你的微信版本、网络环境、账号状态。

## 7. 诚实的部分

AI 在这个项目里帮我完成了：库选型、Docker/WSL 环境搭建、数据库解密路径定位、发送性能归因、九轮代码重构。

但它也**判断错过四次**（ClawBot 形态、日志 ID 含义、等待窗口定成 5–10 秒、想用 UIA 读屏幕），前两次靠查原始文档推翻，后两次靠真实日志和实测推翻。**AI 适合当执行者和放大器，不适合当结论的最终来源。**
